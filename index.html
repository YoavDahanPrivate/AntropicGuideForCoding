Rule 1 · Command explained

/goal: keep working until a condition holds

How it works

  1. /goal <task + when it’s done> starts a turn; the text is Claude’s instruction.
  2. After each turn, a small fast model reads the conversation and judges: met, not yet, or impossible.
  3. It runs no commands and reads no files. Claude’s own output, such as the test log, must show the condition.
  4. Stops when met or impossible, or on /goal clear. Bound it with “or stop after 20 turns”.

Use it for

  • API migrations: until every call site compiles and ctest passes
  • Splitting a big file until each part is under 800 lines
  • Burning down a failing test label until it’s green

Avoid it for

  • Quick interactive edits: you rarely need it in-session
  • Conditions a log can’t show, like “make it robust”
  • Hard guarantees: use a Stop hook or CI that runs the check

good /goal migrate src/rt from ring_buffer to spsc_ring; done when no call site uses ring_buffer and ctest -L rt passes, or stop after 30 turns

bad /goal make the audio path robust

Task already in the conversation, e.g. Claude stopped with failing tests? Then the end condition alone is enough: /goal ctest -L rt passes, or stop after 20 turns.

Source: Claude Code docs, “/goal” and “Best practices”. Evaluator tokens are typically negligible; the main turns are the real cost.

Rule 1 · Command explained

/goal vs. “keep going” in a normal prompt

The difference is who decides the work is done.

Normal prompt/goal
Who checks “done”Claude, as it ends its turnA separate model, after every turn
If Claude stops earlyWaits for youStarts the next turn itself
Typical spanOne turn or a fewMany turns, often unattended
FitsWork you’re watchingLong jobs you walk away from

How you run it

1 · Fresh start: task + when it’s done

/goal migrate src/rt from ring_buffer to spsc_ring; done when no call site uses ring_buffer and ctest -L rt passes, or stop after 30 turns

2 · Rescue: Claude stopped early

> Migrate src/rt from ring_buffer to spsc_ring.
… Claude stops: 3 tests in tests/rt fail …
/goal ctest -L rt passes with 0 failures, or stop after 20 turns

Both rely on a model reading the log. For a hard guarantee, use a Stop hook that runs ctest and blocks the stop. Source: Claude Code docs, “/goal”.

Rule 2 · Context · The rules file

One rules file. It loads when Claude opens real-time code.

.claude/rules/rt.md

---
paths:
  - "src/rt/**/*.{c,cc,cpp,h}"
---

← This frontmatter controls loading. Nothing else in the file does.

# Real-time rules  (a heading, for readers only)
Audio thread = rt_callback() and everything it calls.
A finding = code on the audio thread that breaks a rule.

RT-1 No heap allocation: new/malloc, vector/string growth,
     allocating std::function or lambda captures.
     Allowed in prepare() and constructors.
RT-2 No blocking locks (std::mutex, condition_variable).
     Hand data off via spsc_ring<T,N> (src/rt/ring.h).
RT-3 No I/O or syscalls: printf, std::cout, files.
     Log with rt_log(): lock-free, drained off-thread.
RT-4 Every loop has a fixed bound (constant or block_size).
RT-5 Shared indices are std::atomic: release / acquire.

Not a finding: code off the audio thread, tests/, tools/.

When does it load? Four prompts

> fix the warning in tools/gen.py

Claude edits tools/gen.py. Not loaded: no match.

> audio drops out after resume

Claude reads src/rt/device.cpp. Loads now, and stays in context for the rest of the session.

> /rt-review src/rt/mixer.cpp

The skill opens mixer.cpp. Loads. The skill’s contract points to this same file.

> what’s in src/rt?

Claude only lists the folder. Not yet: opening a file is what counts.

No paths: field? Then it loads at launch, every session, like CLAUDE.md.

Trigger: Claude reads, writes or edits a matching file. Source: Claude Code docs, “How Claude remembers your project”. File contents are illustrative.

Rule 2 · Context

CLAUDE.md: spend it on gotchas

The two-question test, per line

1. Could Claude find this by reading the code?
2. Would it actually go and look?
Both yes → cut the line.

It’s a review you do, not a tool. To test a doubtful line: delete it, start a fresh session, give a typical task, and see if Claude still gets it right. /doctor also flags lines Claude could derive from the code (next slide).

Cut

Write clean, modern C++.
This project uses CMake.
IMPORTANT!!! ALWAYS RUN THE TESTS

Keep

Build: cmake --preset rt-debug
Tests: ctest --preset unit -L fast
generated/ comes from tools/gen.sh: never edit
Wire format is big-endian: use net/endian.h

Aim for under 200 lines. A rule that must always hold belongs in a hook or a test, not in louder wording.

Rule 2 · Commands explained

Three commands to audit your context

/context all

Shows what’s in the context window by category, including which CLAUDE.md, rules and memory files loaded.

Output: a coloured grid plus suggestions.
Edits files: no.

/doctor

Setup checkup: install and settings, unused skills and MCP servers against their context cost, CLAUDE.md lines Claude could derive from the code.

Output: findings and proposed fixes.
Edits files: only after you confirm.

/doctor prompt-audit

Audits CLAUDE.md, rules, skills and agents for instructions written for older models, references to missing files or commands, and contradictions.

Output: findings and proposed edits as a diff.
Edits files: only when you ask.

A ten-minute routine, once per model upgrade

/context all → /doctor prompt-audit → review the diff → apply → rerun one typical task

Source: Claude Code docs, “Commands”, “Skills” and “How Claude remembers your project”. prompt-audit needs Claude Code v2.1.283 or later; it can take a path, e.g. /doctor prompt-audit .claude/skills.

Rule 2 · Example in a C/C++ repo

Layer instructions by where they apply

CLAUDE.md

Repo root · loaded at launch

Build: cmake --preset rt-debug

Never edit generated/; run tools/gen.sh

drivers/CLAUDE.md

Loads when Claude reads or edits a file in drivers/

Touch registers only via hal/regs.h macros, never raw volatile casts.

ISRs: set a flag, defer work.

.claude/rules/rt.md

paths: src/rt/**/*.{c,cc,cpp,h}

No heap, locks or blocking calls in code reachable from rt_callback().

Hand data off via spsc_ring<T,N> (src/rt/ring.h).

How .claude/rules/ loads: every .md under it is discovered, subfolders included. A rule without paths: loads at launch, like CLAUDE.md.

Rule 3 · Skills

What loads when: one request, step by step

Descriptions are always loaded. SKILL.md loads when the description fits the task, or when you type /rt-safety. References load only when a step needs them. Scripts are executed; their code never enters context.

Rule 3 · Skills

A skill is a table of contents,
not an encyclopedia

1 · Always loaded

Name + description

2 · When the description fits the task

SKILL.md, under 500 lines

3 · Only when a step needs it

Reference files · scripts (run, not read)

Description = what it does + when to use it. Not “Helps with code.”

One level deep: link every file straight from SKILL.md.

Evals first: run 3 typical tasks without the skill and note where Claude goes wrong. Write only what fixes that, then rerun the same tasks with the skill.

Rule 3 · Example in a C/C++ repo

A skill that lives next to the code it serves

Layout

src/rt/
├─ mixer.cpp ring.h …
└─ .claude/skills/rt-safety/
   ├─ SKILL.md
   ├─ reference/lockfree.md
   ├─ reference/latency-budget.md
   └─ scripts/rt_lint.sh

SKILL.md

name: rt-safety
description: Checks real-time safety of C/C++ changes in src/rt/. Use when editing audio callbacks or code they call.
1. Run scripts/rt_lint.sh on changed files.
2. Allocation or lock found? Read reference/lockfree.md.
3. Timing-sensitive? Read reference/latency-budget.md.

Can any source folder have its own .claude/skills/? Yes. This one is picked up the first time Claude reads or edits a file in src/rt/, or when you start Claude there.

reference/ = docs for one step, read only when that step applies. scripts/ = tools SKILL.md tells Claude to run; executed, never loaded.

Rule 4 · Effort

Wrong result? Ask one question

First check the context: is the prompt clear, and does Claude have the right files and tools?

Didn’t try hard enough?

It skipped a file, didn’t run the tests, didn’t double-check.

→ Raise the effort

Didn’t know enough?

It had everything it needed, clearly tried, and was still wrong.

→ Use a bigger model (Sonnet → Opus)

Analyst

Checker

  • Parallel work needing fresh context
  • Too many tools or clashing instructions

Additional thoughts · B · Module CLAUDE.md

Write the intent. Claude reads the code itself.

src/rt/mixer/CLAUDE.md

# Mixer
Sums N input streams into the output bus.
Audio thread: RT rules apply. Entry: Mixer::process().

## Invariants
- process() < 0.5 ms at 48 kHz / 64 frames
  (measure: tools/bench_mixer)
- Channel changes arrive via spsc_ring;
  never resized inside process()
## Why
- Gain is smoothed per sample, not per block:
  per-block caused zipper noise
## Don’t
- Remove legacy/old_mixer.cpp: v3 plugin ABI
## Verify
- ctest -L mixer

16 lines. Aim for 10 to 30.

Why each part is there

Invariants

Timing budgets and thread ownership aren’t visible in the source.

Why

Stops Claude from “simplifying” a choice back into the old bug.

Don’t

Code that looks dead but must stay.

Verify

How Claude checks its own work in this module.

Leave out

class Mixer has process(), add_channel() …

Claude reads mixer.h better than a summary describes it. A stale description is worse than none.

Test for every line: could Claude learn this by reading the headers and tests? If yes, delete it. File contents are illustrative.

Additional thoughts · E · Keeping it true

Update it when a line becomes wrong.
Claude proposes, a human approves.

Does this change need an update?

Yes · process() budget 0.5 → 0.3 ms (invariant)

Yes · Mixer moves off the audio thread (ownership)

Yes · New 96 kHz path with its own budget (new constraint)

Yes · old_mixer.cpp finally removed (a Don’t goes)

No · New add_send() within the existing design

No · Refactor, rename or bug fix that keeps the invariants

1 · Trigger, in the root CLAUDE.md

If your change alters an invariant, budget, thread owner or Don’t in a module CLAUDE.md, update it in the same change and say so. Never add code descriptions.

2 · Gate, in CODEOWNERS

src/rt/mixer/CLAUDE.md  <mixer owners>

3 · Drift check, optional

A design-check skill compares the branch diff with the touched modules’ CLAUDE.md and proposes edits before the PR.

4 · Audit, every release

/doctor prompt-audit catches what slipped through.

Why not let Claude commit it alone? Every future session trusts this file. Auto-memory is private, so Claude writes it alone; a module CLAUDE.md is shared, so it’s reviewed.
